## 2. 구조 분석
```
http.mjs ─▶ app.mjs ─▶ db.mjs(Store)
               │
               ├─ text.mjs ─ profile.mjs ─┬─ recommend.mjs ─ rag.mjs ─ kb.mjs ─ knowledge/jobs.mjs
               │                          ├─ review.mjs   ──┘ (근거 가이드 검색)
               │                          ├─ posting.mjs  ── recommend.mjs
               │                          └─ revise.mjs   ── llm.mjs
```
- **의존 방향이 한쪽(위→아래)** 이고 순환 참조가 없습니다. 업무 규칙은 app/각 모듈에, HTTP는 얇은 층입니다. 덕분에 서버 없이 모듈 단위 테스트가 가능합니다(테스트의 대부분이 이렇게 작성됨).
- **규칙 기반 분석 + 검색 + LLM 보조**의 층 분리가 명확합니다. LLM이 없어도 전체 기능이 동작하는 것(NFR-01)이 구조로 보장됩니다.
- **지식(jobs.mjs)이 단일 원천**입니다. 점수용 사전과 검색용 청크가 같은 데이터에서 만들어져 서로 어긋나지 않습니다.

## 3. 잘 된 점
1. 모든 파일 머리와 주요 줄에 "무엇을, 왜" 주석이 있어 설명 가능성이 높습니다.
2. 외부 입력 경계가 한곳(http.mjs `userOf`/`intOf`/`readBody`, app.mjs `prepare`)에 모여 있고, SQL은 전부 바인딩 쿼리입니다(문자열 연결 0건).
3. 소유자 확인이 일관됩니다: 제출·점검·피드백 조회에 항상 `user_id` 조건(IDOR 방지).
4. 트랜잭션: 점검+항목 저장, 기준 데이터 동기화, 제출+추천 저장이 원자적입니다.
5. 화면은 `innerHTML`을 쓰지 않아(DOM API만) XSS 위험이 구조적으로 낮습니다.
6. LLM 출력은 신뢰하지 않고 사후 검증(숫자·기술명 대조)을 거칩니다.
7. 키는 환경변수로만 다루고 오류·로그에 노출하지 않습니다(테스트로 확인).

## 4. 이번 검토에서 발견·수정한 결함 (7건, 모두 회귀 테스트 추가)
| # | 위치 | 결함 | 영향 | 수정 |
|---|---|---|---|---|
| 1 | revise.mjs `apply` | `String.replace(원문, 제안문)`에서 제안문의 `$&`, `$1` 등이 특수 패턴으로 해석됨 | LLM 제안이나 문서에 `$`가 있으면 미리보기 문장이 깨지거나 원문이 중복 삽입 | 함수형 치환으로 글자 그대로 교체 |
| 2 | revise.mjs LLM 응답 처리 | 응답이 빈 줄로 시작하면 "첫 줄"이 빈 문자열 → 정상 제안이 '너무 짧음'으로 폐기 | 일부 모델에서 AI 제안 채택률 저하 | 내용이 있는 첫 줄을 사용 |
| 3 | recommend.mjs | 합친 글의 앞 4,000자만 검색 질의에 사용 | 이력서가 길면 **자소서가 추천 검색에 전혀 반영되지 않음** | 이력서·자소서 각 앞 2,000자씩 사용 |
| 4 | http.mjs 본문 한도 | `/api/analyze` 한도 60KB < 한글 12,000자×2(약 72KB) | 허용한다고 안내한 길이의 입력이 "요청이 너무 큽니다(413)"로 거절 | 한도 100KB로 상향(주석에 계산 근거) |
| 5 | posting.mjs 학력 판정 | "학력 무관(대졸 우대)"처럼 필수가 아닌 문구도 "미충족 가능"으로 단정 | 고졸 지원자에게 잘못된 낙담성 안내 | "학력 무관"·"우대"가 있으면 `check`(직접 확인)로 완화 |
| 6 | db/app | 제출 저장과 추천 저장이 별도 호출 | 추천 저장 실패 시 추천 없는 고아 제출이 남음 | `saveAnalysis` 트랜잭션 |
| 7 | 정리 | 사라진 상수의 고아 주석, 중복 import, 쓰이지 않는 `jobGuide` 필드 | 가독성·혼동 | 제거 |

**테스트의 실효성 점검(변이 테스트):** 새 테스트가 정말 결함을 잡는지 확인하려고 수정을 일부러 되돌려 실행했습니다. 처음에는 4건 중 2건만 잡혀 두 테스트(검색 질의, 본문 크기)가 **통과하지만 아무것도 검증하지 못하는 약한 테스트**임을 발견해 고쳤고(예: 테스트 문서가 한도보다 작았음), 이후 4건 모두 수정 되돌림 시 실패하는 것을 확인했습니다.

## 7. 성능·복잡도
- 추천: 직무 13개 × 사전 대조 + 60청크 BM25 → 수 ms. 최악 입력(12,000자×2, 8,000자 공고)도 40ms 이내(실측).
- 공고 대조: 항목(≤25) × 서류 문장 수의 겹침 계산 — 입력 한도 안에서 충분히 빠름.
- 병목은 **LLM 호출**(문장당 최대 30초, 예산 45초)뿐이며 순차 실행입니다.

## 9. 면접에서 말할 수 있는 코드 품질 포인트
- "경계에서 검증하고, 내부에서는 신뢰한다": 입력 검증은 http/app에 모으고 모듈 내부는 단순하게 유지했습니다.
- "LLM을 믿지 않는다": 결과를 원문과 대조하고 실패하면 규칙 경로로 대체합니다.
- "테스트를 테스트한다": 수정을 일부러 되돌려 보는 변이 점검으로, 통과만 하는 무의미한 테스트 2건을 찾아 고쳤습니다.
- "측정한 것과 못 한 것을 구분한다": 코드 경로 커버리지 98.9%와 실제 모델 품질 검증은 다른 문제입니다.
