## 3. 직무 추천 정확도
평가셋: `samples/eval.json`(쉬움, 직무 사전과 비슷한 용어, 26건), `samples/hard.json`(어려움, 기술명을 풀어 쓴 문장, 10건). 검색 모드 BM25.

| 설정 | 쉬운 셋 Top-1 | 어려운 셋 Top-1 | 어려운 셋 Top-3 |
|---|---|---|---|
| **전체(역량 .40 + 검색 .50 + 행동어 .10)** | 58/58 (100%) | 8/10 (80%) | 10/10 (100%) |
| 역량 사전만 | 58/58 | 3/10 (30%) | 4/10 (40%) |
| 검색(RAG)만 | 58/58 | 8/10 (80%) | 10/10 |
| (참고) 초기 가중치 .60/.25/.15 | 58/58 | 6/10 (60%) | 10/10 |

**해석**
- 사전만으로는 기술명을 풀어 쓴 문서를 거의 못 맞혔고(30%), **RAG 검색이 그 빈틈을 메웠다**. 이것이 RAG를 쓴 가장 큰 실증 근거입니다.
- 어려운 셋 오답: 프론트엔드→PM, QA→백엔드(개발과 테스트가 섞인 문서). 둘 다 정답이 2순위라 Top-3는 100%.
- **한계**: 평가 문서는 작성자가 직접 쓴 가상 데이터, 가중치도 같은 셋으로 골랐음(과적합 가능). 쉬운 셋 100%는 사전을 만든 사람이 만든 문서라 낙관적입니다. 실제 사용자 정확도는 낮을 수 있습니다.

## 4. 보완 제안(LLM) 실측
로컬 Ollama(kanana2:3b)로 데모 문서를 보완한 결과(샘플 1건, 5문장):
- **재측정(로컬 Ollama kanana2:3b, 모의 지원자 P1·P3·P7의 13문장, `node tools/llm_check.mjs`):**
  - 초기(사용자 문서를 system 프롬프트에 포함, 숫자·기술명 검증만): AI 채택 10/13. 그러나 채택된 문장 중 **"MySQL"이 "My민"으로 깨진 문장**과 **문서에 없는 "매장 운영 효율성을 높였습니다"** 같은 날조성 문장이 섞여 있었습니다(검증이 못 잡음).
  - 현재(사용자 문서를 user 메시지의 `<문서>` 구역으로 분리, 영문 단어·성과 표현 검증 추가): AI 채택 9/13. 깨진 기술명과 문서에 없는 성과 주장이 걸러져 **채택률은 약간 내려갔지만 채택된 문장의 신뢰성은 올라갔습니다**(이 점검은 3명·13문장의 관찰이며 일반화할 수 없음).
  - 여전히 못 막는 것: 문서에 없는 **다른 종류의 사실 주장**(예: "안정적인 서비스 운영을 지원했습니다")은 숫자·기술·성과 표현 목록에 걸리지 않으면 통과합니다. 그래서 화면 경고와 사용자 확인이 필요합니다.
- 소형 모델은 문장을 거의 그대로 돌려주거나 일반론을 덧붙이는 경우가 있어, **검증과 규칙 대체가 필수**임을 확인. 소요 시간은 1분 내외(문장 5개).
- Claude·ChatGPT 품질은 키가 없어 미측정(예정).

## 5. 속도
샘플 1건 로컬 측정: 직무 추천 8.5ms, 점검 2.4ms, 규칙 보완 2.1ms. AI 보완은 모델에 따라 수 초~1분.
최악 입력 점검(NFR-02·03): 문서 12,000자×2 분석 16ms, 400줄·8,000자 공고 점검 40ms, 구분자 없는 8,000자 반복 문자열 8~12ms — 정규식 폭주(ReDoS)나 처리 지연 징후 없음.

## 6. 테스트 중 발견·수정한 결함
| # | 결함 | 원인 | 조치 |
|---|---|---|---|
| 1 | 서버를 다시 켜면 시작 실패(FOREIGN KEY) | 기준 데이터 동기화에 INSERT OR REPLACE 사용 → 기존 기록이 참조하는 직무 행 삭제 시도 | UPSERT로 변경, 재시작 회귀 테스트 추가 |
| 2 | 규칙 보완 문장이 "니다: …"로 잘림 | 상투 표현 제거 정규식이 어미 일부만 제거 | 막연한 문장은 빈칸 틀로 교체 |
| 3 | 지원 동기 문장("서버 개발자로 지원합니다")이 수치 보강 대상에 포함 | 동사 단서만 검사 | 과거형·동기 문구 조건 추가 |
| 4 | 내용 없는 문서가 신뢰도 high | 검색 점수가 직무 간 상대값이라 항상 1 | 찾은 역량 수·행동어 비율로 신뢰도 보정 |
| 7 | "5개월", "3년" 같은 근무·수강 기간이 성과 수치로 집계됨(화면 점검에서 발견) | 단위 목록의 '개'가 '개월'과 겹치고 '개월·달'이 단위에 포함 | 기간 표기는 성과에서 제외(단, "3개월에서 1개월로", "2개월 단축"은 성과로 인정), 테스트 3개 추가 |
| 5 | 테스트 서버가 앱 생성 전에 만들어짐 | 훅 순서 의존 | 직접 대기하도록 수정 |
| 6 | AI 제안이 원문과 같은 문장 | 소형 모델 특성 | "원문 동일" 검증 추가 |
| 8 | 날조 검증이 빈칸 표시 `[지표]`를 '데이터 기반 의사결정' 역량으로 오인해 정상 AI 제안을 거절 | 역량 별칭 '지표'가 빈칸 문구와 겹침 | 검증 전에 대괄호 빈칸 제거(모의 평가에서 발견), 회귀 테스트 |
| 9 | 공고 "SQL 활용 능력"이 SQL 없는 서류를 충족 처리 | 'sql'이 다른 역량의 별칭이기도 함 | 다른 역량의 이름과 같은 별칭으로만 잡힌 역량 제외(모의 평가에서 발견), 회귀 테스트 |
| 10 | 같은 이름의 역량이 여러 직무에 있을 때 마지막 직무의 별칭만 남음 | Map에 이름 키로 덮어쓰기 | 별칭 합집합 공통 사전(ALL_SKILLS), 회귀 테스트(12명 모의 평가에서 발견) |
| 11 | 규칙 보완이 업무 역량을 도구처럼 씀("고객 응대를 활용해") | 모든 직무 역량을 '활용' 대상으로 취급 | 영문 도구·기술 이름일 때만 사용, 회귀 테스트 |
| 12 | "채용 또는 행사 운영 경험" 같은 대안 항목이 미충족 처리 | 기술 사전만으로 판정 | 문장 겹침 판정과 비교해 더 좋은 쪽 채택, 회귀 테스트 |
| 13 | 깨진 주소 인코딩(`/%E0%A4%A`)과 JSON이지만 객체가 아닌 본문(`null` 등)이 500 오류 | 예외를 잡지 않음(코드 점검 중 발견) | 400으로 응답, 회귀 테스트 |
