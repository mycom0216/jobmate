# JobMate 모의 사용자 평가 결과

작성일 2026-11-25 · 작성자 반재영 · 실행: `node tools/simulate_eval.mjs --md`

> **이것은 실제 사용자 평가가 아닙니다.** 가상 지원자 6명의 문서를 작성자가 직접 만들어 실제 프로그램 경로(추천→점검→보완→공고 점검)에 통과시킨 **모의 평가**입니다. 설문(유용했나, 믿을 만했나)은 사람만 답할 수 있어 **만들지 않았습니다**. 실제 평가(사용자평가계획 문서)는 12/08~12/19에 별도로 진행합니다.

## 1. 목적과 방법
| 항목 | 내용 |
|---|---|
| 목적 | 실제 평가 전에 (1) 사람이 쓸 법한 다양한 문서에서 결함을 미리 찾고 (2) 객관적으로 측정 가능한 지표를 확인 |
| 대상 | 가상 지원자 6명(`samples/personas.json`): 컴공 졸업, 마케팅 인턴, 매장 판매, 디자인 전공, 경리 아르바이트, 데이터+마케팅 혼합 |
| 문서 | 각자 "수정 전"(막연한 표현·수치 없음)과 "수정 후"(피드백을 반영해 고친 문서) 2종 + 지원할 공고 1건 |
| 측정 | 추천 일치(Top-1/Top-3), 점검 점수 전→후, 보완 제안의 날조 여부, 공고 필수 충족도 전→후, 처리 시간 |
| 설문 | 미실시(사람 필요) |

**요약**
- 추천: 1순위 일치 6/6, Top-3 포함 6/6. 단, 지원자 문서도 작성자가 썼으므로 쉬운 평가셋과 같은 낙관 편향이 있습니다.
- 점검 점수: 평균 41.3 → 80.2(+38.8), 6명 모두 상승. 이는 "고친 문서를 도구가 더 높게 평가하는가"라는 **방향성 확인**이며, 도구가 실제로 글을 좋게 만든다는 증거가 아닙니다("수정 후" 문서도 제가 썼습니다).
- 공고 필수 충족도: 평균 75% → 91.7%.
- 보완 제안 21건 중 날조(새 숫자·새 기술명) **0건**, 처리 시간 평균 약 8ms(AI 미사용 경로).
- P3(판매 경력)만 신뢰도 low: 문서에 직무 단서(기술·성과)가 부족하다는 도구의 안내와 일치.

## 3. 모의 평가로 발견·수정한 결함
| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| 1 | 날조 검증이 **빈칸 표시 `[지표]`** 를 '데이터 기반 의사결정' 역량으로 오인(`지표`가 그 역량의 별칭) | AI가 빈칸 틀을 포함한 정상 제안을 내도 "원문에 없는 기술"로 **잘못 거절**(처음 실행에서 21건 중 15건 오탐) | 검증 전에 대괄호 빈칸을 제거. 빈칸 밖의 새 숫자·기술은 계속 거절. 회귀 테스트 추가 |
| 2 | 공고의 "SQL 활용 능력"이 **SQL이 없는 서류**를 '충족/부분'으로 판정(`sql`이 다른 역량의 별칭이기도 함) | 공고 점검의 충족도가 부풀려짐 | 다른 역량의 "이름"과 같은 별칭으로만 잡힌 역량은 버리고 이름이 일치하는 역량만 사용. 회귀 테스트 추가 |
| 3 | `GA4`, `구글 애널리틱스`, `광고 집행/소재` 표현을 역량으로 인식 못함 | 마케팅 문서의 공고 충족도가 실제보다 낮게 나옴 | 별칭 추가 |

> 주의: 3번은 모의 문서를 보고 별칭을 늘린 것이라 **같은 모의 문서에서 점수가 좋아 보이는 효과**가 있습니다(과적합 가능). P2·P5의 공고 충족도 "전" 100%는 이런 별칭 보강과 문서가 사전과 겹치는 영향이 있어 낙관적으로 봐야 합니다.

## 4. 한계 (결과보고서에 그대로 기재)
1. 지원자 문서와 "수정 후" 문서를 모두 작성자가 만들어 편향이 큽니다. 실제 사용자 문서는 더 다양하고 지저분합니다.
2. 주관 지표(유용성·신뢰·사용성)는 측정하지 못했습니다.
3. 6명 표본으로 일반화할 수 없습니다.
4. 점검 점수 상승은 도구가 규칙으로 보는 요소(수치·STAR·직무 키워드)를 채운 문서가 높게 나오는 것을 보여 줄 뿐, 채용 담당자의 평가와 같다는 뜻이 아닙니다.

## 5. 다음 단계
실제 사용자 3~5명 평가(사용자평가계획) → 이 모의 평가에서 쓴 같은 지표 + 설문 비교 → 결과보고서 4.5절에 모의 평가(예비)와 실제 평가를 **구분해서** 기록.
