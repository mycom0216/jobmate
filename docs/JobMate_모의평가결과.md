# JobMate 모의 사용자 평가 결과

작성일 2026-11-25 · 작성자 반재영 · 실행: `node tools/simulate_eval.mjs --md`

> **이것은 실제 사용자 평가가 아닙니다.** 가상 지원자 12명의 문서를 작성자가 직접 만들어 실제 프로그램 경로(추천→점검→보완→공고 점검)에 통과시킨 **모의 평가**입니다. 설문(유용했나, 믿을 만했나)은 사람만 답할 수 있어 **만들지 않았습니다**. 실제 평가(사용자평가계획 문서)는 가능할 때 별도로 진행합니다.

## 1. 목적과 방법
| 항목 | 내용 |
|---|---|
| 목적 | (1) 사람이 쓸 법한 다양한 문서에서 결함을 미리 찾고 (2) 객관적으로 측정 가능한 지표를 확인 |
| 대상 | 가상 지원자 12명(`samples/personas.json`): 컴공 졸업, 마케팅 인턴, 매장 판매, 디자인 전공, 경리 아르바이트, 데이터+마케팅 혼합, 비전공 부트캠프, 앱 테스트, 학생회(인사), 고졸 상담원, **정보가 거의 없는 짧은 문서**, 시스템 관리(데브옵스) |
| 문서 | 각자 "수정 전"(막연한 표현·수치 없음)과 "수정 후"(피드백을 반영해 고친 문서) 2종 + 지원할 공고 1건 |
| 특수 케이스 | P11은 직무를 맞히는지가 아니라 **단서가 부족할 때 신뢰도 low로 안내하는지**를 확인. P10(고졸)과 공고의 "대졸 이상" 요건으로 학력 안내를 확인 |
| 측정 | 추천 일치(Top-1/Top-3), 점검 점수 전→후, 보완 제안의 날조 여부, 공고 필수 충족도 전→후, 처리 시간 |
| 설문 | 미실시(사람 필요) |

**요약**
- 추천: 1순위 일치 12/12(P11은 "low로 안내" 기준), Top-3 포함 12/12. 단, 지원자 문서도 작성자가 썼으므로 쉬운 평가셋과 같은 낙관 편향이 있습니다.
- 신뢰도: 단서가 적은 P3·P10·P11이 low로 안내됨 — 도구의 안내와 문서 실제 상태가 일치.
- 점검 점수: 평균 36.8 → 78(+41.3), 12명 모두 상승. 이는 "고친 문서를 도구가 더 높게 평가하는가"라는 **방향성 확인**이며, 도구가 실제로 글을 좋게 만든다는 증거가 아닙니다("수정 후" 문서도 제가 썼습니다).
- 공고 필수 충족도: 평균 63.8% → 85.4%. 고졸 지원자(P10)에게 "대졸 이상" 요건은 요건 목록이 아니라 **학력 조건 안내**로 분리되어 표시됨.
- 보완 제안 40건 중 날조(새 숫자·새 기술명) **0건**, 처리 시간 평균 약 6ms(AI 미사용 경로).

## 3. 모의 평가로 발견·수정한 결함 (총 6건)
| # | 결함 | 영향 | 조치 |
|---|---|---|---|
| 1 | 날조 검증이 **빈칸 표시 `[지표]`** 를 '데이터 기반 의사결정' 역량으로 오인 | 정상 AI 제안을 **잘못 거절**(6명 평가에서 21건 중 15건 오탐) | 검증 전에 대괄호 빈칸 제거 |
| 2 | 공고의 "SQL 활용 능력"이 SQL이 없는 서류를 '충족/부분'으로 판정(공유 별칭) | 공고 충족도 부풀림 | 다른 역량의 이름과 같은 별칭으로만 잡힌 역량 제외 |
| 3 | `GA4`, `구글 애널리틱스`, `광고 집행/소재` 표현 인식 누락 | 마케팅 문서 충족도 과소 | 별칭 추가 (**모의 문서를 보고 늘림 → 과적합 가능**) |
| 4 | **같은 이름의 역량이 여러 직무에 있을 때 별칭이 마지막 직무 것만 남음**(`Map`에 이름 키로 덮어쓰기) | '커뮤니케이션'의 면담·조율·공감 표현을 인식 못해 인사·CS 문서의 충족도 과소 | 직무별 별칭을 합집합으로 합친 공통 사전(`ALL_SKILLS`) |
| 5 | 규칙 보완 문장이 업무 역량을 "도구"처럼 씀("고객 응대를 활용해 …") + 원문에 없는 표현을 끼워 넣음 | 어색한 문장, 검증에서 날조로 분류(12명 평가에서 3건) | 영문 도구·기술 이름일 때만 "X을(를) 활용해", 아니면 `[사용한 도구·방법]` |
| 6 | "채용 **또는** 행사 운영 경험"처럼 대안이 있는 항목을 기술 사전만으로 판정해 한쪽 경험만 있는 서류를 미충족 처리 | 인사 지원자(P9) 공고 충족도 0% | 기술 판정이 낮으면 문장 겹침 판정과 비교해 더 좋은 쪽 채택 (기술 태그는 그대로 표시) |

4~6번은 지원자를 6명에서 12명으로 늘리자 드러난 결함입니다. **표본이 늘면 새로운 결함이 나온다는 것 자체가, 실제 사용자 평가가 더 필요하다는 근거**입니다.

> 주의: 3번처럼 모의 문서를 보고 사전을 보강한 부분은 같은 문서에서 점수가 좋아 보이는 효과가 있습니다. P2·P5의 공고 충족도 "전" 100%도 문서가 사전과 겹친 영향이 있어 낙관적으로 봐야 합니다.

## 4. 한계 (결과보고서에 그대로 기재)
1. 지원자 문서와 "수정 후" 문서를 모두 작성자가 만들어 편향이 큽니다. 실제 사용자 문서는 더 다양하고 지저분합니다.
2. 주관 지표(유용성·신뢰·사용성)는 측정하지 못했습니다.
3. 12명 표본으로 일반화할 수 없습니다.
4. 점검 점수 상승은 도구가 규칙으로 보는 요소(수치·STAR·직무 키워드)를 채운 문서가 높게 나오는 것을 보여 줄 뿐, 채용 담당자의 평가와 같다는 뜻이 아닙니다.
5. 12명 중 직무가 한 개씩만 다뤄져 같은 직무 안의 문서 다양성은 확인하지 못했습니다.

## 5. 다음 단계
가능하면 실제 사용자 3~5명 평가(사용자평가계획) → 같은 지표 + 설문 비교 → 결과보고서에 모의 평가(예비)와 실제 평가를 **구분해서** 기록. 실제 평가를 못 하는 경우에는 "모의 평가로 대체, 주관 평가는 향후 과제"로 명시합니다.
